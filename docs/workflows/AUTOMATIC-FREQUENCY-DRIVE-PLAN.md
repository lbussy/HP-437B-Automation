# Automatic frequency × drive sweep implementation plan

Proposed November 23, 2026. Implement in **Operator-guided radio sweep → Frequency × drive setting**. The operator selects one transmitter and RF output, reviews the conducted test setup, and explicitly starts a run. Automatic mode applies each drive setting, tunes a finite carrier, checks readiness, measures with the HP 437B, and verifies shutdown. Keep the existing per-point confirmation path available for manual operation. Generate a full PDF when requested, during the run's reporting stage or later from its saved capture.

The first intended physical campaign is the original **52-point Pico direct-GPIO sweep** on the 13 requested bands. Measure the selected RF output through a documented conducted fixture that meets both the source loading and the sensor input limits. The [30 m bench record](../validation/30M-POWER-20261123.md) supplies evidence for one frequency and drive. Pi and Si5351 are additional selectable source profiles for this same workflow. The plan covers the named hardware and this test only. Keep scheduling, station and advertised WSPR power, other sweep modes, POWER REF workflows, ordinary logging, meter calibration tables, and deployment outside the work.

Derive the nominal single-tone RF test carrier as **dial frequency + 1,500 Hz** exactly once, in integer Hz. Send that absolute carrier through the explicit custom RF path for both Pico and Pi. Keep random placement off. Use the RF carrier for frequency admission and meter correction, and record both the dial and carrier in the plan and reports. ## 2. Device controls

- **Pico direct GPIO.** Use authenticated Consumer-Radio with the existing Control/1 one-shot job operations (`/api/control/v1/jobs`) and negotiated GPIO-drive management. Check that this carrier admits the required operations for the selected firmware and setup. Use fresh session/request/job IDs, explicit CLAIM/LOAD/ARM, and job-specific ABORT/RELEASE. Bind ARM to current device clock admission and boot identity. Group the automatic run by drive to minimize restarts. Capture the initial saved and boot-active drive and revision. Refuse a pending restart or differing saved/active settings instead of activating unrelated pending changes. When a drive change is needed, verify idle, unowned, and RF off, write the drive with the fresh target/revision, and use the existing explicit restart transaction. Show the planned saves, restarts, and restoration up front for approval as part of Start. Wait for the same device, a new boot, active drive, no pending restart, clock admission, and the expected RF pin and engine. After ARM, verify the boot-bound pad observation before accepting data. A target lacking effective drive evidence cannot complete an automatic point. Validate configuration prerequisites without provisioning or creating unrelated settings. Release each job before a drive change. Restore and verify the original drive after success or a known-safe stop, using the same preapproved save/restart process. For an ambiguous save, restart, or launch, reconcile using fresh identity and status without replaying a mutation. Keep progression stopped if any affected state remains unknown.
- **Pi finite tuning and drive.** Reuse WsprryPi's loopback-only bounded Test Tone contract through a locally configured, authenticated connection to its host. Extend only that request, if needed, with an optional transient integer drive in mA. Bind that value to the existing immutable tone plan and controller generation. Preserve requests that omit it and existing saved configuration semantics. Use the existing ownership and terminal cleanup path with recurrence disabled and no previous output eligible for restoration. Wait for the matching active runtime event beyond the start acknowledgement. Verify terminal state, output inactive, and any restoration result before continuing. Use a generation-bound early stop. If the existing stop path cannot bind the request to the expected generation, add that check to the bounded-tone owner path so a delayed cancel cannot stop later work.
- **Legacy Pi pads.** Translate mA to the existing pad code at the WsprryPi engine boundary. For BCM2835/36/37 and RP3A0, code 0–7 represents 2–16 mA in steps of two. For BCM2711, code 0–7 represents 1–8 mA. Keep existing persisted indexes intact and correct the 1–8 mA labels for this sweep and its receipts. Verify the DRIVE bits through the engine. The legacy register affects the GPIO bank, so verify bank ownership for the chosen fixture and restore the previous pad state through the same owner. [Raspberry Pi pad controls](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html#drive-strength-list)
- **RP1.** Pass nominal mA unchanged through WsprryPi's current GPCLK provider, validate the provider mask, and record effective drive evidence from that path. Reuse the provider lease, STOP, and quiescence. [RP1 peripherals](https://pip-assets.raspberrypi.com/categories/892-raspberry-pi-5/documents/RP-008370-DS-1-rp1-peripherals.pdf)
- **Si5351.** On Pi, map 2/4/6/8 mA to WsprryPi levels 1/2/3/4. On Pico, apply the selected mA to the existing validated Si5351 configuration without changing the rest of the pin/module allocation, then restart and read back the boot-active setting and selected clock's drive/enable state through the owning engine. Ordinary Pico firmware currently gates the QRP Labs Rev. 6, 25 MHz TCXO, CLK0 profile to 8 mA. Keep that gate in ordinary firmware until conducted checks qualify 2/4/6 mA on the same named module profile using the existing engineering path. Then extend that exact production profile's allowed drive list, retaining its other conditions. A build or target that has not passed those checks reports the unavailable values explicitly. A register ACK, reset, or lost connection is insufficient evidence that an independently powered module stopped. Require verified clock disable and a prepared independent way to remove its RF if control becomes uncertain. [Si5351 AN619](https://www.skyworksinc.com/-/media/Skyworks/SL/documents/public/application-notes/AN619.pdf)

Keep native hardware access in WsprryPi/WsprryPico. The HP project owns orchestration, meter handling, evidence, and reports. Implement adapters against checked-in owner contracts and test against the explicit version pair. Use a current authenticated Pico carrier that admits the existing one-shot job operations and supports the selected management operations. Verify that at preflight. If an operation is missing, address only the missing narrowly typed operation in its owner, using existing control and authentication. The earlier plain LAN WTP bench helper is historical evidence. Bind the configured carrier to device identity and credentials, keep secrets out of requests displayed in the UI and out of logs, and use a bounded reauthentication/reconnect path after an authorized restart. Restore only the fields owned by the run, with fresh compare-and-set checks. A concurrent edit or unknown resulting state requires reconciliation and a new Start.

## 3. Sweep lifecycle and measurement

1. **Preflight.** Freeze and show the plan, target, engine/pin or CLK output, accepted fixture and expected input bounds, and selected operating settings. Verify RF off and conflicting schedules/controllers idle or disabled, including across planned Pico restarts. Reserve the sweep in the service and use the existing device authority for each source transaction. Canonicalize and use the same configured meter resource and lock root as preparation and POWER REF. Let the ZERO runner acquire and release its own resource lease. After healthy closure, acquire the lease for capture and recheck meter state before arming. Hold it through each RF and capture transaction, including final confirmed stop. Apply the same canonical lease to manual guided starts on that resource so a second managed job cannot bypass it from a different run directory. Preflight still checks that external control applications are closed. If another workflow or controller claims either resource in between, stop before RF. Check USB identity, meter preparation and sensor serial, POWER REF off, and scientific measurement limits before enabling the source. Begin with fresh supervised ZERO while RF is off and require the existing completion/closure evidence. Reuse the prepared CAL. For the current fixture, require the 8482A MY41094127 profile. Apply its explicit frequency correction with the existing logger mechanism and record its basis. Set and check the factor and other meter preparation with RF off where possible, then perform fresh status and sample checks after activation. Use the frozen requested RF carrier in integer Hz for the factor when any accepted backend adjustment stays within the declared per-point frequency tolerance and would produce the same rounded factor. Refuse or replan and revalidate the point before keying otherwise. Keep the source-specific correction and limits explicit in the captured setup.
2. **Acquire.** Verify same-job active state and effective frequency/drive before treating any readings as RF-on. Retain the dial frequency, requested RF carrier, backend-realized RF where reported, and independently measured RF only if available. Use the 437B's delayed trigger and require a complete parsed numeric reply and appropriate fresh status before advancing. After a change require two successive complete readings to agree within the greater of 1% of magnitude or a declared absolute tolerance based on meter resolution and RF-off noise. Use three settling attempts and three retained samples per point as proposed defaults, subject to the preflight timing budget. A timeout fails the point. A numeric plateau at or below the stated measurement floor is a limited observation and may be shown in W without claiming quantified RF power. It must not pass an above-floor readiness test or be retried indefinitely. Require evidence that all credited RF-on reads finished within the matching active job window, with time to request stop before its hard end. Unexpected terminal state or an unresolvable timing boundary invalidates affected rows. Record finite RF-off checks before the sweep and after its final confirmed stop. Keep them separate from the retained RF-on samples and leave baseline subtraction off. Preserve the meter's range/filter settings and the observed read times, and retain raw frames and correction receipts. Report below-range or missing values explicitly and keep negative baseline values in W.
3. **Bound output and stop.** Establish source-side hard tone limits, separate startup/settling/sample/cleanup deadlines, and a finite whole-run limit. Reserve the complete cleanup window even on cancellation, with source stop dispatched independently of a blocked VISA call. For Si5351, the finite job limits the commanded tone and cannot guarantee hardware off after a failed I²C write. Keep the operator present at the prepared independent shutdown, and record uncertain RF explicitly if the owning engine cannot verify disable. Establish the read budget from the manual's filter/range conditions plus scoped baseline and pilot evidence. Allow up to 30 seconds for RF-off acquisitions where the filter and range call for it. For RF-on, require a bounded timing profile whose sum fits the driver limit: startup allowance + correction/status/probe work during RF + all settling and retained read budgets + sample spacing + stop reserve. Avoid double-counting only when the same setup sample is explicitly used for the settling comparison. The prior roughly 7.4-second RF-off reads are evidence against a five-second default, not a worst-case bound for every range. If the budget cannot fit, show the conflict and allow the operator to select fewer samples or a separately prepared, verified acquisition setting before Start. A numeric timeout limit is a deadline rather than a fixed wait. Publish the calculated maximum run time and update progress after each phase without silently increasing that maximum. Each tone must fit the effective backend maximum, including Pi's current 60-second bounded tone limit. Reject impossible combinations before keying. Never extend an active tone to recover a slow meter. Stop through the matching job/generation as soon as samples are in, independently of meter cleanup. RF-off confirmation and successful cleanup are required before proceeding. Use normal TR3/Go To Local on healthy meter sessions. Continue without manual LOCAL when closure is healthy. An accepted Go To Local receipt alone does not establish front-panel state. Unknown RF or meter state, identity changes, loss of admission, failed restoration, and cancellation stop progression, preserve partial receipts, and require reconciliation before any new Start.
4. **Seal evidence.** Add a versioned automatic capture record with the same native logger artifacts and report model. Reuse the manual confirmation path for manual runs. Automatic rows carry the human-started run authorization and machine-observed drive, active-window, and stop receipts, with no fabricated operator confirmations. Bind records to the immutable matrix, target, boot or controller generation, and unique point/job ID. Keep each requested point and its outcome, plus issued/resolved settings, correction and setup, meter replies/timing/statistics, device receipts and state transitions, and cleanup. The loader recomputes coverage and statistics and verifies those bindings from sealed evidence. Older manual records remain readable. Use explicit states for measured, limited, failed, and not reached so partial reports do not look complete. Maintain separate capture and report outcomes. A report failure leaves the sealed capture usable for report regeneration without equipment access.

## 4. Optional complete PDF

Add **Include PDF** (off by default in the new combined-sweep UI) to the combined workflow's report options and the matching local client/re-report path. Select it for the intended 52-point campaign. Preserve the previous PDF behavior when legacy clients omit the new option, and allow later export from any compatible sealed combined capture. Generate HTML, CSV, and JSON in either case. A selected PDF contains the full requested matrix in mW and dBm, per-point statistics and status, a comparison plot when enabled, setup and identities, applied factors, and coverage and limitations. Repeat headings across pages and show missing cells visibly. Coverage distinguishes requested, attempted, measured, and limited or missing points. Evaluate no pass/fail without supplied DUT criteria. Label the power plane as sensor input and describe unfiltered harmonics and any characterized fixture loss. Share the existing PDF style, licensed fonts, and evidence bindings through a guided-only multi-page renderer. Derive the PDF and other formats from the same validated point results. Use stable inputs and deterministic pagination. Record the actual page count in the PDF metadata and keep capture hashes intact. Keep other reports’ existing behavior.

Move PDF dependency checks to PDF-dependent actions so this combined workflow can run without ReportLab when PDF is off. Keep plot dependencies conditional on plots. Preserve the one-page summary and existing ZIP verification behavior for old bundles and other workflows. Extend the existing portable ZIP validator narrowly for the new combined report type so it verifies its actual PDF page count, capture binding, and artifact manifest. PDF-off output has no PDF or PDF-dependent ZIP and no broken download links. Persist the option in the versioned job request, surface it in history and guided re-report, and distinguish unavailable dependencies from completed capture. A later guided re-report accepts the option anew. Report settings, dependency failure, or repeated export operate solely on saved data after capture. Install or check the optional dependencies before Start when those outputs are requested.

## 5. Delivery and acceptance

1. **Plan and control contract.** Add exact matrix/source metadata, extend owner controls only where missing, and check the mapping for every legal drive plus representative invalid values and wrong engine/board. Verify all 13 dial-to-carrier pairs and that both controls receive the absolute carrier, including 60 m at 5366200 Hz. Cover Pico save/ACK/restart, Pi transient drive, Si5351 clock selection, RP1 mask, lost replies and stale sessions. Run the relevant controller suites and the Pi/Pico contract integration suites if the shared contract changes.
2. **Offline orchestration and reports.** Run the 52- and 104-point matrices through injected controls/meter using production entry points. Assert request order, no premature sampling, unique point IDs, settling/timeout and cancellation behavior, hard duration bounds, independent STOP, off/readback proof, failure evidence, settings restoration, and protection from concurrent or stale control. Test optional PDF on/off, absent optional dependencies, legacy re-report/package compatibility, and reproducible results from sealed evidence. Render and inspect complete and partial PDFs including the 104-point case.
3. **Selected hardware.** Separately authorize conducted testing on a named board/engine and fixture, starting with RF-off and single-tone checks, then verify each claimed drive setting, timely shutdown, and the widest frequency changes for that setup. Record board, firmware, provider/kernel where relevant, fixture, and the exact readback and RF checks. Progressively enable additional profiles within the requested matrix as evidence allows. Run the 52-point Pico campaign after preceding readiness checks and deliver the selected PDF with traceable capture. Keep software support and hardware qualification distinct for each Pi family, Si5351 host/profile, and RP1 provider. If the actual target refuses a requested band/drive or lacks a safe timing window, report the specific blocker and the measured coverage. Retain the requested scope without adding qualification overrides or substituting another test.
